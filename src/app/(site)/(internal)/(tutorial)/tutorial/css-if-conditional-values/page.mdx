## Introduction

Conditional styling in CSS has always meant one of two workarounds: toggling a class from JavaScript, or duplicating
a whole rule inside `@media` or `@supports`. The new **`if()`** function collapses that into a single property
value. It picks between several values, right inside a declaration, based on a condition CSS can already evaluate:
a media query, a feature check, or — the genuinely new part — the current value of a custom property.

<Info title="New to custom properties?">
  A custom property is a variable you define yourself, such as `--priority: high`. It's written with two leading
  dashes, inherits down the tree like `color` does, and is read back with `var(--priority)`. `if()` can test its
  value directly, which is what makes the examples below work. For another function that picks a value for you,
  see [One-Line Theme-Aware Colors with `light-dark()`](/tutorial/light-dark-color-scheme).
</Info>

## Basic Usage

<CodeBlock language="css">
{`
  .badge {
    background: if(
      style(--priority: high): crimson;
      style(--priority: medium): darkorange;
      else: seagreen
    );
  }
`}
</CodeBlock>

How to read it:

- **Each branch is a `condition: value` pair**, and branches are separated by semicolons.
- **Branches are checked top to bottom, and the first match wins.** Later branches are never considered once one
  matches.
- **`else:` is the catch-all**, used when no condition matches.

Change `--priority` — from JavaScript, or from another CSS rule — and the background follows. There's no class
list to keep in sync with the state.

The state can even come straight from the markup. With
[typed `attr()`](/tutorial/css-typed-attr#data-types-for-type), `--priority: attr(data-priority type(<custom-ident>), low);`
reads `<div class="card" data-priority="high">` into the custom property that `style()` tests, with no inline style
or JavaScript at all.

## The Three Condition Types

<CodeBlock language="css">
{`
  .card {
    width: if(
      media(width > 900px): 32rem;
      supports(color: oklch(0.7 0.15 30)): 24rem;
      else: 100%
    );
  }
`}
</CodeBlock>

- **`media()`** takes the same conditions as `@media`, such as viewport width or `prefers-color-scheme`.
- **`supports()`** takes the same conditions as `@supports`, checking whether the browser understands a property
  and value.
- **`style()`** checks a custom property's current value. This is what makes `if()` new: a *value*, not a whole
  block, that reacts to state.

<Warning title="There is no container() condition">
  `if()` can't test container queries. For styles that depend on a parent's size, [`@container`](/post/css/container-queries-deep-dive) is still the
  only option.
</Warning>

### Where `style()` Reads From

`style()` tests the custom property's value **on the element being styled** — whether that value was set on the
element itself or inherited from an ancestor. That's why the demo below can set `--priority` once on the card and
have the badge inside it react. (Container style queries work differently: they read the value from the
container.)

## Branch Order Matters

Because the first matching branch wins, put the most specific conditions first. A broad condition placed early hides
every narrower one after it:

<CodeBlock language="css">
{`
  /* ❌ The 900px branch never runs: any width over 900px is also over 600px */
  .panel {
    padding: if(
      media(width > 600px): 1.5rem;
      media(width > 900px): 2.5rem;
      else: 1rem
    );
  }

  /* ✅ Narrowest condition first */
  .panel {
    padding: if(
      media(width > 900px): 2.5rem;
      media(width > 600px): 1.5rem;
      else: 1rem
    );
  }
`}
</CodeBlock>

<RainbowDivider />

## Always Pair It with a Fallback

Browser support is still limited, so declare a plain value first and the `if()` version second:

<CodeBlock language="css">
{`
  .badge {
    background: gray; /* Every browser reads this */
    background: if(
      style(--priority: high): crimson;
      else: gray
    );
  }
`}
</CodeBlock>

This protects two different cases in two different ways:

- **Browsers without `if()`** can't parse the second declaration, so they drop it while reading the stylesheet and
  only the first one ever reaches the cascade. No `@supports` block is needed.
- **Browsers with `if()`** use the second declaration, and the first one is simply overridden. If no branch matches
  and there's no `else`, the property becomes *invalid at computed-value time* and behaves as if it were never
  set. The earlier fallback does **not** come back — so always include an `else`.

## Going Further

### Combining Conditions

Conditions can be combined with `and`, `or`, and `not`, just like in `@media`:

<CodeBlock language="css">
{`
  .toolbar {
    gap: if(
      media(width > 900px) and style(--density: compact): 0.5rem;
      not media(width > 900px): 0.25rem;
      else: 1rem
    );
  }
`}
</CodeBlock>

### Using `if()` Inside Other Values

`if()` stands in for part of a value, so it can sit inside a shorthand, a `calc()`, or a custom property:

<CodeBlock language="css">
{`
  .card {
    /* Only the inline margin changes */
    margin: 0 if(media(width > 900px): 2rem; else: 1rem);

    /* One branch of a larger calculation */
    padding: calc(if(style(--density: compact): 0.5rem; else: 1rem) * 2);

    /* Resolve once, reuse everywhere */
    --accent: if(style(--priority: high): crimson; else: royalblue);
    border-color: var(--accent);
    color: var(--accent);
  }
`}
</CodeBlock>

`if()` also works inside the body of a [custom function](/tutorial/css-custom-functions-at-function), so a condition that many rules share can live in
one `@function` instead of being repeated in every declaration.

## Relationship to @media, @supports and @container

<CodeBlock language="css">
{`
  /* Before: the same rule duplicated per breakpoint */
  .panel { padding: 1rem; }
  @media (width > 900px) {
    .panel { padding: 2rem; }
  }

  /* After: one declaration */
  .panel {
    padding: if(media(width > 900px): 2rem; else: 1rem);
  }
`}
</CodeBlock>

The at-rules still own conditional *rules*: new selectors, several declarations at once, or restructuring a layout.
`if()` is for a conditional *value* inside a rule you're already writing — exactly the case that used to force
either duplicating the whole rule or falling back to JavaScript. If the value should scale smoothly rather than jump
between fixed options, [`min()`, `max()`, and `clamp()`](/tutorial/min-max-clamp-functions) are usually the better
fit.

<RainbowDivider />

## Where Should You Use This?

- A single custom property (`--variant`, `--size`, `--state`) driving several unrelated declarations across a
  component, without a class for every combination
- Small value swaps (a color, a spacing step, a font-weight) that don't justify duplicating an entire rule under
  `@media`
- Replacing a JavaScript-driven inline style or class toggle whose only job was picking between a few known CSS
  values

## Production Considerations & Edge Cases

* **Check support before relying on it.** `if()` shipped in Chrome and Edge 137. Check current Firefox and Safari
  support on [Can I use](https://caniuse.com/?search=if()) before depending on it without a fallback.
* **Declare the fallback first, and always include `else`.** The fallback covers browsers without `if()`; `else`
  covers browsers with it. You need both (see [Always Pair It with a Fallback](#always-pair-it-with-a-fallback)).
* **Feature-detect with `@supports` when a whole block depends on it.** `@supports (color: if(else: red))` is true
  only in browsers that understand `if()`.
* **`style()` only reads custom properties in current browsers.** A test like `style(color: red)` on a standard
  property isn't supported yet; branch on a `--custom-property` instead.
* **It's a value, not a control-flow statement.** `if()` can't leave out a declaration or a selector. For that,
  `@media`, `@supports`, and `@container` are still what you reach for.

## Frequently Asked Questions

<Details summary="Is CSS if() the same as @if in Sass?">
  No. Sass's `@if` runs once at build time on Sass variables, and only its result reaches the browser. CSS `if()` is
  evaluated by the browser for every element, and it re-evaluates whenever a custom property, media condition or
  feature check it depends on changes.
</Details>

<Details summary="Can I nest one if() inside another?">
  Yes. A branch's value can be another `if()`, just as it can be a `calc()`. If you find yourself nesting more than
  one level, combining conditions with `and` or moving the logic into a [custom function](/tutorial/css-custom-functions-at-function)
  is usually easier to read.
</Details>

<Details summary="Can I transition between the values of an if()?">
  Yes. `if()` resolves to an ordinary computed value, so when the matching branch changes, a `transition` on that
  property runs just as it would after a class change.
</Details>

<Details summary="Why does my style() condition never match?">
  The most common cause is the value not matching exactly as written. `--priority: "high"` is a quoted string, so it
  doesn't match `style(--priority: high)`. Check the custom property's value in DevTools, and make sure it's set on the
  element being styled or one of its ancestors.
</Details>

## Key Takeaway

`if()` fills the one gap the conditional at-rules never covered: a single value, inside a declaration you're
already writing, chosen by a condition — most usefully the live value of a custom property. Order branches from
most to least specific, always end with `else`, and keep a plain fallback declared first while browser support
catches up.
