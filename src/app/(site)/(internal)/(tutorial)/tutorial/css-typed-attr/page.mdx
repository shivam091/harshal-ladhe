## Introduction

CSS has had `attr()` for decades, but only in one place. Inside the `content` property of a `::before` or `::after`
pseudo-element, it reads an HTML attribute and inserts it as text — which is how
[CSS-Only Tooltips with `attr()` and `content`](/tutorial/css-attr-content-tooltips) turn a `data-tooltip` attribute
into a tooltip with no JavaScript:

<CodeBlock language="css">
{`
  .has-tooltip::after {
    content: attr(data-tooltip);
  }
`}
</CodeBlock>

Anywhere else, `attr()` did nothing. `width: attr(data-width)` was invalid, because the classic function always
returns a **string**, and a string isn't a width. So data that already lived in the HTML — a progress percentage, a
column count, a brand colour from a CMS — had to be copied into inline styles or custom properties before CSS could
use it.

**Typed `attr()`** removes that limit. Tell it what type to read the attribute as, and it returns a real CSS value —
a length, a colour, a number, an angle — usable in **any property, on any element**.

## Classic vs Typed

<CodeBlock language="html">
{`
  <div class="meter" data-progress="65"></div>
`}
</CodeBlock>

<CodeBlock language="css">
{`
  /* Classic: a string, only useful as text */
  .meter::after {
    content: attr(data-progress) "%";
  }

  /* Typed: a real percentage, usable as a width */
  .meter::before {
    inline-size: attr(data-progress %, 0%);
  }
`}
</CodeBlock>

The attribute is the same `"65"` in both. The classic form inserts it as the characters "6" and "5"; the typed form,
told to read it with the `%` unit, turns it into `65%` — a value `inline-size` understands.

## The Syntax

<CodeBlock language="css">
{`
  attr(<attribute-name> <type>?, <fallback>?)
`}
</CodeBlock>

The type is what's new. It can be one of three things:

| Type                  | Reads the attribute as…                         | Example                                     |
| --------------------- | ----------------------------------------------- | ------------------------------------------- |
| `type(<syntax>)`      | Any CSS data type, parsed from its text          | `attr(data-colour type(<color>))`           |
| A unit, like `px`, `%`, `deg` or `ms` | A bare number with that unit added | `attr(data-size px)` turns `"24"` into `24px` |
| `raw-string`          | A string, exactly as written                     | `attr(data-label raw-string)`               |

With no type at all, `attr()` behaves exactly as it always has and returns a string, so existing `content: attr(…)`
code keeps working unchanged.

### Data Types for `type()`

`type()` accepts the same data types used to
[register custom properties with `@property`](/tutorial/typed-custom-properties-at-property#syntax):

| Data type                  | Attribute value examples           |
| -------------------------- | ---------------------------------- |
| `<color>`                  | `"#2dd4bf"`, `"rebeccapurple"`, `"oklch(0.75 0.15 60)"` |
| `<length>`                 | `"2rem"`, `"24px"`                 |
| `<percentage>`             | `"65%"`                            |
| `<length-percentage>`      | `"2rem"` or `"50%"`                |
| `<number>`, `<integer>`    | `"1.5"`, `"3"`                     |
| `<angle>`                  | `"45deg"`, `"0.25turn"`            |
| `<time>`                   | `"200ms"`, `"1.5s"`                |
| `<custom-ident>`           | `"card-42"`                        |

Alternatives can be combined with `|`, as in `type(<length> | auto)`.

### Unit or `type()`?

They differ in **where the unit lives**. With `type(<angle>)`, the attribute must include it: `data-angle="45deg"`.
With the `deg` unit, the attribute is a bare number and CSS adds the unit: `data-angle="45"`. Use a unit when the
HTML comes from somewhere that only deals in numbers, like a database or a range input's value.

## Fallbacks

The second argument is used whenever the attribute is **missing**, or its value **doesn't parse** as the requested
type:

<CodeBlock language="css">
{`
  .tag {
    --tag: attr(data-colour type(<color>), indigo);
    color: var(--tag);
    border: 1px solid var(--tag);
  }
`}
</CodeBlock>

`data-colour="teal"` gives a teal tag; `data-colour="not-a-colour"`, or no attribute at all, gives an indigo one.
Without a fallback, an invalid or missing attribute makes the whole declaration invalid at computed-value time — the
same as an undefined `var()` — and the property falls back to its inherited or initial value. Give every typed
`attr()` a fallback unless that's what you want.

## Patterns Worth Knowing

### Passing a Value Down to Children

`attr()` reads the attribute of the element being styled — or, for a pseudo-element, the element it belongs to. To
use an attribute on a **child**, read it on the parent into a custom property, and let the child inherit it:

<CodeBlock language="css">
{`
  .dial {
    --angle: attr(data-angle type(<angle>), 0deg);
  }

  .dial-needle {
    rotate: var(--angle);
  }
`}
</CodeBlock>

The attribute is resolved on `.dial`, so the needle inherits the finished `45deg`, not the instruction to read an
attribute it doesn't have.

### Layout from Content Data

<CodeBlock language="css">
{`
  .gallery {
    display: grid;
    grid-template-columns: repeat(attr(data-columns type(<integer>), 2), 1fr);
  }
`}
</CodeBlock>

A CMS or component prop can set `data-columns="4"` on the markup, with no class per column count and no inline
style.

### Unique Names for View Transitions

Every element in a view transition needs a unique `view-transition-name`. Most list items already have a unique
`id`, and `<custom-ident>` turns it into a name:

<CodeBlock language="css">
{`
  .card {
    view-transition-name: attr(id type(<custom-ident>), none);
  }
`}
</CodeBlock>

One rule names every card, instead of one generated inline style per item. Two details are worth knowing. An `id`
that isn't a valid CSS identifier — `id="42"` starts with a digit — doesn't parse as a `<custom-ident>`, so that
card gets the `none` fallback and simply isn't animated on its own. And if the names only need to be unique, not
predictable, Chromium's `view-transition-name: match-element` does the same job without any attribute. Reach for
`attr(id …)` when the name has to match across pages, as in a cross-document view transition, where the browser can
only pair old and new elements that share a name.

### Branching on an Attribute with `if()`

A `<custom-ident>` read into a custom property is a value that
[`if()` and `style()`](/tutorial/css-if-conditional-values) can test, so a single attribute can pick between
several values without a class for each:

<CodeBlock language="css">
{`
  .card {
    --priority: attr(data-priority type(<custom-ident>), low);
    background: if(
      style(--priority: high): #fee2e2;
      style(--priority: medium): #fef3c7;
      else: #f1f5f9
    );
  }
`}
</CodeBlock>

`<div class="card" data-priority="high">` turns the card red, with no inline style and no JavaScript.

### Staggering in a Custom Order

[`sibling-index()`](/tutorial/sibling-index-count-functions) staggers animations by an element's position in the
DOM. When the order should come from data instead — a rank, a priority, the order results arrived in — store it in
an attribute:

<CodeBlock language="css">
{`
  .result {
    animation: fade-in 0.3s ease both;
    animation-delay: calc(attr(data-order type(<integer>), 0) * 80ms);
  }
`}
</CodeBlock>

### Transitions Come for Free

A typed `attr()` produces an ordinary computed value, so when the attribute changes, any `transition` on that
property runs, just as it would after a class change:

<CodeBlock language="css">
{`
  .meter::before {
    inline-size: attr(data-progress %, 0%);
    transition: inline-size 0.2s ease;
  }
`}
</CodeBlock>

Updating `data-progress` from JavaScript (or a framework re-render) animates the bar to its new width. The progress
bar in the sandbox works this way.

## `attr()` or a Custom Property?

The same progress bar can be written with an inline custom property, which every modern browser supports today:

<CodeBlock language="html">
{`
  <div class="meter" style="--progress: 65%"></div>
`}
</CodeBlock>

Both work. Reach for typed `attr()` when the value is **already in the HTML for another reason** — a `data-*`
attribute read by JavaScript too, or a native one such as `colspan` — so it doesn't need repeating in a `style`
attribute. It
also keeps styling out of the markup entirely, which helps under a Content Security Policy that blocks inline styles.
Reach for a custom property when the value only exists for styling, or when the component must work in every
browser right now.

## Browser Support and Fallbacks

Typed `attr()` shipped in Chromium browsers (Chrome and Edge 133) in 2025. Firefox and Safari don't support it yet
at the time of writing; there, only the classic `content: attr(…)` form works.

In a browser without support, a declaration using typed `attr()` is invalid and dropped, so the rule above it in the
cascade wins. Declare a sensible default first, then the `attr()` version:

<CodeBlock language="css">
{`
  .gallery {
    grid-template-columns: repeat(3, 1fr);
    grid-template-columns: repeat(attr(data-columns type(<integer>), 3), 1fr);
  }
`}
</CodeBlock>

When a whole block of styles depends on it, test for support with `@supports`:

<CodeBlock language="css">
{`
  @supports (width: attr(data-x type(<length>), 0px)) {
    /* typed attr() styles */
  }
`}
</CodeBlock>

### The Custom Property Trap

The "default first" trick doesn't work when `attr()` is stored in a custom property, as in the tag and dial
examples. An unregistered custom property accepts any value at all, so an unsupporting browser keeps
`--tag: attr(data-colour type(<color>), indigo)` as plain text instead of dropping it. Every `var(--tag)` then
becomes invalid at computed-value time, the property resets to its inherited or initial value, and the default
declared before it is ignored.

Two fixes work. Wrap the custom property in the `@supports` test above, or register the property with `@property`
so that it has a type and an initial value:

<CodeBlock language="css">
{`
  @property --tag {
    syntax: "<color>";
    inherits: false;
    initial-value: indigo;
  }

  .tag {
    --tag: attr(data-colour type(<color>), indigo);
    color: var(--tag);
  }
`}
</CodeBlock>

A registered `<color>` property can't hold the text of an unsupported function, so browsers without typed `attr()`
throw that value away and use `indigo`, the `initial-value`. For everything else registration changes, see
[Animate and Type-Check CSS Variables with `@property`](/tutorial/typed-custom-properties-at-property).

## Common Pitfalls

### 1. Leaving Out the Type

`inline-size: attr(data-progress)` is still a string, and still invalid outside `content`. Typed behaviour only
starts when you name a type or a unit.

### 2. Putting the Unit in the Wrong Place

`data-angle="45"` with `type(<angle>)` fails, because `45` isn't an angle — and `data-angle="45deg"` with the `deg`
unit fails, because `45deg` isn't a bare number. Match the attribute's format to the form of `attr()` you chose.

### 3. Expecting It to Build URLs

`background-image: url(attr(data-src))` doesn't work, and won't. Values from `attr()` can't be used to make URLs, so
an attribute an attacker can control can't be turned into a network request by your CSS. Keep image URLs in `src`
attributes or in your stylesheet.

### 4. Reading an Attribute from the Wrong Element

`attr()` only ever looks at the element being styled. A child can't read its parent's attribute directly; resolve it
on the parent into a custom property, as in the dial pattern above.

### 5. Expecting It to Track Live Form Values

`attr()` reads the HTML **attribute**, not the JavaScript property behind it. When someone drags a range slider or
types into a field, the element's `value` property changes but its `value` attribute keeps the value it started
with, so `attr(value …)` doesn't move. If CSS needs to follow user input, copy the value into a `data-*` attribute
(or a custom property) in an `input` event listener, as the sandbox does.

### 6. Using It as the Only Source of Meaning

A bar whose width comes from `data-progress` looks like a progress indicator, but assistive technology sees only a
`<div>`. Styling doesn't carry meaning, so pair the visual with a native `<progress>` or `<meter>`, or with ARIA —
the sandbox's bar has `role="img"` and an `aria-label` that's updated alongside the attribute.

## Frequently Asked Questions

<Details summary="Can a user-controlled attribute inject CSS through attr()?">
  No. The attribute is parsed only as the type you asked for, so it can't add declarations or break out of the
  value. Anything that doesn't parse as that type uses the fallback, and `attr()` values can never be turned into
  URLs.
</Details>

<Details summary="Can I use typed attr() in a media query?">
  No. Like `var()`, `attr()` only works in property values. It can't be used in selectors, in `@media` conditions or
  in other at-rule preludes.
</Details>

<Details summary="Can I place grid items from an attribute?">
  Yes. Read the attribute as a `<custom-ident>`, as in `grid-area: attr(data-area type(<custom-ident>), auto)`, and
  each item is placed in the named area its markup asks for.
</Details>

<Details summary="Is changing an attribute slower than changing a class?">
  Not in any way you'd notice. Both make the browser recalculate styles for the element, and typed `attr()` only adds
  parsing one short attribute value during that recalculation.
</Details>

## Key Takeaway

Classic `attr()` could only print an attribute as text. Typed `attr()` — `attr(data-colour type(<color>), indigo)`,
`attr(data-progress %, 0%)` — reads it as a real CSS value for any property on any element, with a fallback for
missing or invalid values. Use it when the data already lives in your HTML, give it a fallback, declare a default
before it for browsers without support — or register the property when `attr()` lives in a custom property — and
keep using the classic form for text in `content`.
