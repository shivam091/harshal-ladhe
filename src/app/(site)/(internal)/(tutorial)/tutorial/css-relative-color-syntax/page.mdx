## Introduction

Most design systems start with one brand colour and then need a dozen more: a lighter tint for backgrounds, a darker
shade for hover states, a translucent version for focus rings, maybe a complementary accent. Traditionally each one
was picked by hand and stored as its own hex code, so changing the brand colour meant updating every variant too.

**Relative colour syntax** lets CSS work those variants out for you. You hand a colour function an existing colour,
it splits that colour into its channels, and you write the new colour in terms of them:

<CodeBlock language="css">
{`
  :root {
    --brand: #6366f1;
    --brand-light: oklch(from var(--brand) calc(l + 0.2) c h);
    --brand-dark: oklch(from var(--brand) calc(l - 0.15) c h);
    --brand-ring: oklch(from var(--brand) l c h / 40%);
  }
`}
</CodeBlock>

Change `--brand` and the whole palette follows.

## The Syntax

<CodeBlock language="css">
{`
  <color-function>(from <origin-color> <channel> <channel> <channel> / <alpha>?)
`}
</CodeBlock>

The `from` keyword is what makes a colour relative. The origin can be any valid colour: a hex code, a named colour,
`currentColor`, a `var()`, or even another relative colour. CSS converts it into the colour space of the function
you're writing, and then exposes each channel as a **keyword** you can use in that position:

| Function    | Channel keywords        | Ranges the keywords resolve to                |
| ----------- | ----------------------- | --------------------------------------------- |
| `rgb()`     | `r` `g` `b` `alpha`     | `r`, `g`, `b`: 0–255; `alpha`: 0–1            |
| `hsl()`     | `h` `s` `l` `alpha`     | `h`: 0–360; `s`, `l`: 0–100                   |
| `hwb()`     | `h` `w` `b` `alpha`     | `h`: 0–360; `w`, `b`: 0–100                   |
| `lab()`     | `l` `a` `b` `alpha`     | `l`: 0–100; `a`, `b`: roughly -125–125        |
| `lch()`     | `l` `c` `h` `alpha`     | `l`: 0–100; `c`: 0–150; `h`: 0–360            |
| `oklab()`   | `l` `a` `b` `alpha`     | `l`: 0–1; `a`, `b`: roughly -0.4–0.4          |
| `oklch()`   | `l` `c` `h` `alpha`     | `l`: 0–1; `c`: 0–0.4; `h`: 0–360              |

Every keyword resolves to a **plain number**, with no unit. That's what lets you do maths on it with `calc()`.

### Copying a Colour

Writing the channels back unchanged gives you the same colour, converted:

<CodeBlock language="css">
{`
  /* The same indigo, now expressed in oklch() */
  color: oklch(from #6366f1 l c h);
`}
</CodeBlock>

On its own that isn't very useful. It becomes useful once you replace one of the channels.

## Changing One Channel

### Transparency

The most common job is making a colour translucent. Before relative colours, that meant storing the colour twice —
once as hex, once as separate RGB numbers for `rgba()`. Now you only replace the alpha:

<CodeBlock language="css">
{`
  .card:focus-visible {
    outline: 3px solid oklch(from var(--brand) l c h / 40%);
  }
`}
</CodeBlock>

### Lighter and Darker

Change the lightness channel to get tints and shades:

<CodeBlock language="css">
{`
  .button {
    background: var(--brand);
  }

  .button:hover {
    background: oklch(from var(--brand) calc(l - 0.08) c h);
  }
`}
</CodeBlock>

### Rotating the Hue

Add to the hue for related colours. Half a turn gives the complementary colour, and thirds of a turn give a triad:

<CodeBlock language="css">
{`
  :root {
    --complement: oklch(from var(--brand) l c calc(h + 180));
    --triad-1: oklch(from var(--brand) l c calc(h + 120));
    --triad-2: oklch(from var(--brand) l c calc(h + 240));
  }
`}
</CodeBlock>

Hues wrap around, so `calc(h + 240)` on a hue of `280` gives `520`, which CSS treats the same as `160`.

### Muting a Colour

Lower the chroma to make a colour greyer — useful for disabled states or subtle borders:

<CodeBlock language="css">
{`
  .button:disabled {
    background: oklch(from var(--brand) l calc(c * 0.3) h);
  }
`}
</CodeBlock>

## Why `oklch()` Rather Than `hsl()`?

You can write every example above with `hsl()` instead, and it'll work. The difference is in what "lightness"
means.

In `hsl()`, lightness is a mathematical property of the RGB values, not how bright a colour looks to a person. Pure
yellow and pure blue both have an HSL lightness of 50, yet the yellow looks far brighter. So adding the same `20` to
`l` gives visibly different results depending on which colour you started with.

`oklch()` is designed around human perception. Equal changes to its `l` look like equal changes in brightness,
whatever the hue. That makes it the better choice for a palette generated by formula, where you can't check every
colour by eye — and it's why the examples here use it. For colours that switch with the theme, see
[One-Line Theme-Aware Colors with `light-dark()`](/tutorial/light-dark-color-scheme).

<Info title="Watch the units in hsl()">
  In `hsl(from …)`, the `s` and `l` keywords are plain numbers like `50`, not percentages like `50%`. So write
  `calc(l + 10)`, not `calc(l + 10%)` — mixing a number and a percentage makes the `calc()` invalid.
</Info>

## Patterns Worth Knowing

### A Palette from a Single Token

Generate an entire scale from one custom property, so a theme only needs to set that one value:

<CodeBlock language="css">
{`
  :root {
    --brand: #6366f1;

    --brand-100: oklch(from var(--brand) 0.95 calc(c * 0.3) h);
    --brand-300: oklch(from var(--brand) 0.8 calc(c * 0.7) h);
    --brand-500: var(--brand);
    --brand-700: oklch(from var(--brand) 0.45 c h);
    --brand-900: oklch(from var(--brand) 0.3 calc(c * 0.8) h);
  }

  .theme-forest {
    --brand: #16a34a;
  }
`}
</CodeBlock>

Here the lightness is replaced with a **fixed number** rather than adjusted with `calc()`. That makes every step of
the scale land at the same brightness whatever the brand colour is, so `--brand-100` is always a pale background
colour and `--brand-900` is always dark enough for text.

<Warning title="Custom properties resolve where they're declared">
  `--brand-100` is calculated on `:root`, using the `--brand` that `:root` sees. Setting `--brand` on
  `.theme-forest` doesn't change `--brand-100` inside it, because the inherited `--brand-100` is already a finished
  colour. Declare the derived properties on the same selector as each theme — for example
  `:root, .theme-forest { --brand-100: … }` — so they're worked out again wherever `--brand` changes.
</Warning>

### Translucent `currentColor`

`currentColor` works as an origin, so a component can draw borders and backgrounds that match its text colour
without knowing what that colour is:

<CodeBlock language="css">
{`
  .badge {
    color: var(--status-colour, teal);
    background: oklch(from currentColor l c h / 12%);
    border: 1px solid oklch(from currentColor l c h / 40%);
  }
`}
</CodeBlock>

### Readable Text on Any Background

Because each channel is a number, you can pick a value based on it. This sets text to black on light backgrounds
and white on dark ones:

<CodeBlock language="css">
{`
  .swatch {
    background: var(--bg);
    color: oklch(from var(--bg) clamp(0, (0.62 - l) * 1000, 1) 0 0 / 1);
  }
`}
</CodeBlock>

When the background's lightness is above `0.62`, `(0.62 - l) * 1000` is negative and clamps to `0` (black). Below
it, the result is a large positive number that clamps to `1` (white). Chroma and hue are set to `0`, giving a pure
grey, and `/ 1` keeps the text opaque even if the background is translucent. It's a simple brightness threshold
rather than a full contrast check, so test it with your own colours.

## Relative Colours or `color-mix()`?

`color-mix()` blends two colours, so `color-mix(in oklch, var(--brand), white 30%)` also gives a lighter brand
colour. The two overlap, but they're suited to different jobs:

| Use…                        | When you want to…                                                  |
| --------------------------- | ------------------------------------------------------------------ |
| `color-mix()`               | Blend towards another colour: white, black, or a second brand colour |
| Relative colour syntax      | Set or adjust a single channel precisely: fixed lightness, rotated hue, exact alpha |

Mixing with white also lowers the chroma, so `color-mix()` tints look slightly washed out, while a relative colour
that only changes `l` keeps the colour's full intensity.

## Browser Support

Relative colour syntax works in every major browser: Chrome and Edge 119, Firefox 128 and Safari 16.4 onwards.
Safari versions before 18 didn't accept `currentColor` as the origin, so add a plain fallback colour before any rule
that relies on it:

<CodeBlock language="css">
{`
  .badge {
    background: rgb(0 128 128 / 12%);
    background: oklch(from currentColor l c h / 12%);
  }
`}
</CodeBlock>

## Common Pitfalls

### 1. Using Percentages in `calc()`

Channel keywords are numbers. `calc(l + 10%)` fails; `calc(l + 0.1)` in `oklch()`, or `calc(l + 10)` in `hsl()`,
works.

### 2. Mixing Up Ranges Between Spaces

`l` is `0`–`1` in `oklch()` but `0`–`100` in `lch()` and `hsl()`. A step of `0.1` that's sensible in `oklch()` does
almost nothing in `hsl()`. Pick one colour function per palette and stick with it.

### 3. Leaving the Gamut

Pushing lightness or chroma too far can produce a colour the screen can't display. Browsers bring it back in range
automatically, but the result may be a different colour than you expect. Keep chroma modest at very high or very low
lightness, where screens can show the least saturation.

### 4. Forgetting That Alpha Carries Over

If you leave out the `/ <alpha>` part, the new colour keeps the origin's alpha. Derive black-or-white text from a
40% translucent background and the text comes out 40% translucent too. Write `/ 1` whenever the result must be
opaque.

### 5. Expecting Derived Properties to Update in Children

As covered in the warning above, a custom property that uses `var(--brand)` is calculated once, where it's declared.
Re-declare the derived properties wherever `--brand` changes.

## Key Takeaway

Relative colour syntax — `oklch(from var(--brand) calc(l + 0.2) c h)` — takes a colour apart into its channels and
lets you rebuild it with some of them changed. Use it to derive tints, shades, translucent versions and related
hues from a single token, write it in `oklch()` so equal steps look equal, remember that channel keywords are plain
numbers, and redeclare derived properties wherever the source colour changes.
