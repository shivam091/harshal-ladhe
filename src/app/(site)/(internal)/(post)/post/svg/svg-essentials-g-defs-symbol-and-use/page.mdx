## Why SVG Needs Grouping and Reuse

Every SVG document you've built so far in this series has been a flat list of shapes: a `path` here, a `circle` there, each one fully spelled out in the markup. That works fine for a handful of shapes, but it falls apart fast once a document needs to repeat an icon a dozen times, apply one transform to a whole illustration, or keep a gradient definition separate from the shape that uses it.

SVG solves this with four container elements that don't draw anything new on their own — they organize and reuse the shapes you already know:

* **`g`** groups elements together so a shared `transform`, `fill`, `opacity`, or event handler can apply to the whole group at once, instead of being repeated on every child.
* **`defs`** holds elements that exist purely to be *referenced* — nothing inside a `defs` block is rendered where it's defined.
* **`symbol`** and **`use`** together form SVG's native "component" system: define a reusable template once, then stamp out as many independently-styled instances of it as you like. This predates the idea of a "component" in any JavaScript framework — SVG has had it since its earliest specification.

<Quote>
  `g`, `defs`, `symbol`, and `use` don't add new geometry to SVG's vocabulary — they add structure, letting the shapes you already know scale from "a few hand-written elements" to "a real, reusable graphics system."
</Quote>

By the end of this post, you'll know when to reach for each of these, how `use` actually behaves under the hood, and how to build a small icon sprite system the SVG-native way — no icon font, no repeated markup.

## `g`: Grouping and Shared Attributes

The `g` element (short for "group") is the simplest of the four. It draws nothing itself — it's a container that lets a set of child elements share attributes, a transform, or an event listener as if they were one unit.

### One Transform, Many Shapes

Without `g`, moving or rotating a multi-shape icon means recalculating the coordinates of every single shape inside it. With `g`, you transform the group once, and every child moves together, keeping their coordinates relative to each other exactly as authored:

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <g transform="translate(20, 10) rotate(15)">
      <rect x="0" y="0" width="40" height="24" fill="#6366f1" />
      <circle cx="40" cy="0" r="6" fill="#4338ca" />
      <line x1="0" y1="24" x2="40" y2="24" stroke="#4338ca" stroke-width="2" />
    </g>
  </svg>
`}
</CodeBlock>

The `rect`, `circle`, and `line` above were authored as if the group's origin were `(0, 0)` — moving and rotating the whole icon is a one-line change to the `g`, not three separate edits.

### Shared Presentation Attributes

The same idea applies to presentation attributes. Set `fill`, `stroke`, or `opacity` on a `g`, and every child that doesn't set its own value for that attribute inherits it:

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <g fill="#10b981" opacity="0.85">
      <circle cx="30" cy="50" r="18" />
      <circle cx="70" cy="50" r="18" />
    </g>
  </svg>
`}
</CodeBlock>

Both circles are green at 85% opacity without repeating `fill` and `opacity` on each one. A child can still override any inherited attribute locally — inheritance flows one direction, from the group down to its children, never back up.

<Info title="Remember">
  `g` groups **behavior**, not just geometry:

  * A shared `transform` moves the whole group as a unit.
  * Shared presentation attributes (`fill`, `stroke`, `opacity`, …) cascade down to children that don't override them.
  * The group itself has no visual geometry — remove every child and the `g` renders nothing.
</Info>

### Nested Groups

Groups can nest inside other groups, and each level's transform composes with the ones above it. This is how you build up complex illustrations in layers — an outer group positions the whole illustration on the canvas, while inner groups handle the local transforms of each sub-part:

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <g transform="translate(50, 50)">
      <!-- Body, positioned relative to the outer group's new origin -->
      <g transform="rotate(20)">
        <rect x="-15" y="-25" width="30" height="50" rx="6" fill="#6366f1" />
      </g>
      <!-- Head, positioned relative to the same outer origin, independent rotation -->
      <circle cx="0" cy="-35" r="10" fill="#f59e0b" />
    </g>
  </svg>
`}
</CodeBlock>

The body's `rotate(20)` only affects the body — the head keeps its own position relative to the outer group's `translate`, completely unaffected by the body's local rotation. Nesting groups is how you isolate a transform to exactly the part of the illustration it should touch.

### `g` as an Event-Handling Boundary

Because `g` is a real element in the DOM, it can carry its own event listeners — and a click, hover, or focus event anywhere inside the group bubbles up through it just like it would through a `div` wrapping several HTML elements.

That makes `g` the natural boundary for "this icon is one clickable thing," even when the icon itself is built from several separate shapes:

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <g class="icon-button" role="button" tabindex="0">
      <circle cx="50" cy="50" r="35" fill="#6366f1" fill-opacity="0.15" />
      <path d="M40,35 L65,50 L40,65 Z" fill="#4338ca" />
    </g>
  </svg>
`}
</CodeBlock>

<CodeBlock language="javascript">
{`
  document.querySelector(".icon-button").addEventListener("click", () => {
    // One handler for the whole play-button icon, regardless of whether the
    // click landed on the background circle or the triangle inside it.
    playVideo();
  });
`}
</CodeBlock>

One listener on the `g` covers clicks on the background circle *and* the triangle, without needing a listener on each shape or a check for which child was the actual target. This is the same delegation pattern you'd use with a `div` wrapping several HTML children — `g` just gives you the equivalent boundary inside SVG.

<Warning title="g is not a hit-testing shortcut for everything">
  A click only lands on a `g` if it lands on one of its *painted* children. An empty region inside the group's visual bounding box — the gap between the circle and the triangle above, for instance — does not trigger the group's listener unless something is actually painted there (or `pointer-events` is set to treat the group as a single hit area).
</Warning>

## `defs`: Define Once, Reference Anywhere

`defs` (short for "definitions") is a container with one very specific rule: **nothing inside a `defs` block is rendered where it's written.** It exists purely to hold elements that other parts of the document will *reference* — by `id` — rather than draw directly.

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <defs>
      <!-- Defined, but not drawn here -->
      <linearGradient id="sky" x1="0%" y1="0%" x2="0%" y2="100%">
        <stop offset="0%" stop-color="#60a5fa" />
        <stop offset="100%" stop-color="#1e3a8a" />
      </linearGradient>
    </defs>

    <!-- The gradient only appears once something references it -->
    <rect x="10" y="10" width="80" height="80" fill="url(#sky)" />
  </svg>
`}
</CodeBlock>

If you moved that `linearGradient` outside of `defs` and left it as a sibling of the `rect`, nothing would change visually — a gradient has no geometry of its own to paint. But that's specific to gradients. Put a `path` or a `circle` inside `defs`, and it disappears entirely, because `defs` suppresses direct rendering for *any* element it contains:

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <defs>
      <!-- This circle is never painted, no matter how it's styled -->
      <circle id="dot" cx="50" cy="50" r="10" fill="#f43f5e" />
    </defs>
  </svg>
`}
</CodeBlock>

That circle is completely invisible until something references `#dot` — most commonly a `use` element, which is where the next section picks up.

<Info title="The one thing that makes something a defs">
  There's no special "definition mode" attribute involved. What makes an element part of a `defs` block is simply that it's a child of `defs` — that placement is what tells the renderer "don't paint this in place, only when something else points at it." The same `circle`, `path`, or `linearGradient` markup renders normally the moment it's a direct child of `svg` or `g` instead.
</Info>

`defs` is the natural home for anything meant to be referenced rather than drawn directly:

* Gradients and patterns, referenced via `fill="url(#id)"` or `stroke="url(#id)"`.
* Filters, referenced via `filter="url(#id)"`.
* Clip paths and masks, referenced via `clip-path="url(#id)"` and `mask="url(#id)"`.
* Reusable shapes and `symbol` templates, referenced by `use href="#id"`.

<Warning title="An id alone doesn't require defs">
  You don't strictly need `defs` for `use` to work — any element with an `id`, anywhere in the document, is a valid reference target. `defs` is a convention (and a very good one) for keeping "things meant to be referenced" visually and organizationally separate from "things meant to be drawn where they sit." An element sitting in `defs` with no `id` at all is unreachable and dead weight in the document — always pair `defs` content with an `id`.
</Warning>

## `symbol` and `use`: SVG's Native Component System

This is where reuse in SVG becomes genuinely powerful. `symbol` defines a reusable template — complete with its *own* `viewBox` — and `use` stamps out an instance of it wherever you want, at whatever size, position, and style that instance needs, without touching the original definition or any other instance.

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <defs>
      <symbol id="star-icon" viewBox="0 0 24 24">
        <path d="M12 17.27L18.18 21l-1.64-7.03L22 9.24l-7.19-.61L12 2 9.19 8.63 2 9.24l5.46 4.73L5.82 21z" />
      </symbol>
    </defs>

    <use href="#star-icon" x="10" y="10" width="24" height="24" fill="#f59e0b" />
  </svg>
`}
</CodeBlock>

### Why `symbol` Carries Its Own `viewBox`

A plain `g` has no coordinate system of its own — it just inherits whatever coordinate space it's placed into. A `symbol` is different: its `viewBox` defines a self-contained coordinate system, the same way the outer `svg` element's `viewBox` does. That's what lets a `use` instance scale a `symbol` to *any* `width`/`height` and have its internal geometry rescale proportionally to fit — exactly like an `svg` document embedded via `img`, rather than raw markup being stretched.

That's the core difference from just wrapping shapes in a `g` and giving it an `id`: a `g` has no `viewBox`, so a `use` targeting a `g` reproduces its geometry at 1:1 scale (`x`/`y`/`transform` can move or scale it, but there's no independent internal coordinate system to resize against). A `symbol` gives every instance an independent "canvas" to scale into, driven by that instance's own `width`/`height`.

### How `use` Stamps Out Instances

Each `use` element referencing the same `symbol` is completely independent. Position, size, rotation, and even color can differ from one instance to the next, and none of it touches the shared definition:

<CodeBlock language="xml">
{`
  <use href="#star-icon" x="10" y="10" width="16" height="16" fill="#f59e0b" />
  <use href="#star-icon" x="40" y="10" width="24" height="24" fill="#6366f1" transform="rotate(15 52 22)" />
  <use href="#star-icon" x="70" y="10" width="32" height="32" fill="#10b981" />
`}
</CodeBlock>

Three completely different-looking stars, one `path` written exactly once. Try it below — each instance has its own fill and its own transform, and changing one never touches the other two or the original `symbol`:

<Info title="Remember">
  `symbol` + `use` in one line:

  **Define once, with its own `viewBox`. Stamp out as many independently-sized, independently-styled instances as you need.**

  This is the same mental model as a component in a UI framework — a template plus props — except it's been part of the SVG spec since SVG 1.1, long before component-based UI libraries existed.
</Info>

## `use` Without `symbol`

`use` isn't limited to referencing a `symbol`. It can target *any* element in the document that has an `id` — a `path`, a `g`, a `rect`, even another `use`. Reaching for `symbol` only makes sense once you actually need that independent `viewBox`-driven scaling; for simple duplication, a plain element reference is all `use` needs:

<InteractiveSvgPanel slug="use-without-symbol-demo" />

Notice that toggling the duplicate's fill off doesn't make it fall back to the original's blue — it falls back to black, SVG's default fill. That's a subtle but important detail: a `use` instance does **not** inherit styling from the *context the original element was authored in* (here, a `g fill="#6366f1"` wrapping the original `path`). It only inherits from its own position in the document — the `use` element's own ancestors, or an explicit attribute set directly on the `use` tag itself.

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <!-- Original: colored via its own <g>'s inherited fill -->
    <g fill="#6366f1">
      <path id="leaf-shape" d="M0,20 C0,8 8,0 20,0 C20,12 12,20 0,20 Z" transform="translate(15,40)" />
    </g>

    <!-- Duplicate: does NOT pick up the blue from the <g> above — it needs its own fill -->
    <use href="#leaf-shape" transform="translate(45,40)" fill="#f59e0b" />
  </svg>
`}
</CodeBlock>

<Warning title="use doesn't clone the original's rendering context">
  A `use` element re-renders the *geometry* of its target, not the DOM position it happened to sit in. If the original picks up its appearance from a wrapping `g`'s inherited attributes rather than its own explicit ones, that inherited appearance does not travel with the reference — only attributes set directly on the referenced element itself, or on the `use` element, apply to the duplicate.
</Warning>

## Nested `svg`

An `svg` element can be nested inside another `svg`, establishing its own completely independent `viewBox` for that region — effectively a "viewport within a viewport." The outer document places the nested `svg` with `x`, `y`, `width`, and `height`, exactly like any other element, but everything drawn *inside* it lives in its own coordinate system, unrelated to the outer one:

<InteractiveSvgPanel slug="nested-svg-viewport-demo" />

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 100">
    <!-- Outer content, in the outer 100 x 100 coordinate system -->
    <rect x="5" y="5" width="90" height="90" fill="none" stroke="gray" />

    <!-- A self-contained mini-diagram, placed at (20, 20), sized 40 x 40,
         with its OWN 0-50 coordinate system inside that box -->
    <svg x="20" y="20" width="40" height="40" viewBox="0 0 50 50">
      <rect width="50" height="50" fill="#6366f1" fill-opacity="0.1" />
      <circle cx="25" cy="25" r="15" fill="none" stroke="#4338ca" stroke-width="2" />
    </svg>
  </svg>
`}
</CodeBlock>

This is useful whenever you want to embed a self-contained piece of graphics — a small chart, an icon with its own internal grid, a mini-map — at a specific position, without recalculating every one of its internal coordinates against the outer document's coordinate space. Author the inner diagram once, in whatever coordinate system is convenient for it, then place the whole thing with a single `x`/`y`/`width`/`height` on the nested `svg`.

<Info title="How is this different from symbol + use?">
  A nested `svg` is drawn exactly where it's written — there's no separate "definition" and "instance" step. `symbol` + `use` is built for *repeating* the same template multiple times; a nested `svg` is built for embedding *one* self-contained region with its own coordinate system, drawn once, in place.
</Info>

## `switch` for Conditional Rendering

`switch` is a narrower, more legacy-leaning tool: it evaluates its children in order and renders **only the first one** whose test attribute passes — `requiredFeatures`, `requiredExtensions`, or `systemLanguage`. Every other child is skipped entirely, not just hidden.

The most practical use is picking a localized label based on the user's browser language:

<CodeBlock language="xml">
{`
  <svg viewBox="0 0 100 40">
    <switch>
      <text systemLanguage="fr" x="10" y="25" font-size="14">Bonjour</text>
      <text systemLanguage="ja" x="10" y="25" font-size="14">こんにちは</text>
      <!-- No systemLanguage attribute — this is the fallback if nothing above matched -->
      <text x="10" y="25" font-size="14">Hello</text>
    </switch>
  </svg>
`}
</CodeBlock>

Only one `text` element renders — whichever is the first match for the user's language, with the unconditioned last entry acting as the default. This is a minor corner of SVG compared to everything else in this post, and in most modern applications you'd reach for a JavaScript-driven localization layer instead — but it's worth knowing `switch` exists for cases where the SVG itself needs to make that call without any scripting.

## A Practical Icon Sprite System

Put `defs`, `symbol`, and `use` together, and you get the SVG-native alternative to an icon font or copy-pasting the same inline markup everywhere: a single `defs` block of `symbol` icons — either at the top of the page or in one sprite file loaded once — referenced by `use` wherever an icon is needed.

<SvgSnippet>
{`
  <svg viewBox="0 0 220 60" width="440" height="120">
    <defs>
      <symbol id="icon-star" viewBox="0 0 24 24">
        <path d="M12 17.27L18.18 21l-1.64-7.03L22 9.24l-7.19-.61L12 2 9.19 8.63 2 9.24l5.46 4.73L5.82 21z" />
      </symbol>
      <symbol id="icon-heart" viewBox="0 0 24 24">
        <path d="M12 21s-6.7-4.35-9.3-8.1C.6 9.9 1.9 6 5.4 6c2 0 3.4 1.1 4.1 2.4C10.2 7.1 11.6 6 13.6 6c3.5 0 4.8 3.9 2.7 6.9C18.7 16.65 12 21 12 21z" />
      </symbol>
    </defs>

    <use href="#icon-star" x="10" y="18" width="24" height="24" fill="#f59e0b" />
    <use href="#icon-star" x="50" y="18" width="24" height="24" fill="#6366f1" />
    <use href="#icon-heart" x="90" y="18" width="24" height="24" fill="#f43f5e" />
    <use href="#icon-heart" x="130" y="18" width="24" height="24" fill="#10b981" />
    <use href="#icon-star" x="170" y="18" width="24" height="24" fill="#be185d" />
  </svg>
`}
</SvgSnippet>

Two `symbol` definitions, five `use` instances, and not one `path` string repeated. Update the star's `d` attribute in the one `symbol` and every instance across the entire page updates with it — the same "single source of truth" benefit a component gives you in a UI framework, achieved with plain markup.

<Info title="One sprite file, loaded once">
  In a real app, the `defs` block of `symbol` icons is often pulled out into its own `icons.svg` file, injected into the page once (or referenced via `use href="/icons.svg#icon-star"`), so every page on the site shares the same definitions instead of re-declaring them per-page.
</Info>

## Where Should You Use This?

`g`, `defs`, `symbol`, and `use` earn their keep in a specific set of situations:

* **Icon systems and sprite sheets.** A `defs` block of `symbol` icons, referenced by `use` throughout the UI, is the direct SVG equivalent of an icon font — without the font-loading overhead or the accessibility pitfalls of encoding icons as text glyphs.
* **Repeated decorative elements that should stay in sync.** Five stars in a rating widget, a grid of dots in a background pattern, a row of identical dividers — define the shape once as a `symbol` (or a plain referenced element), and every instance updates the moment the master definition changes.
* **Complex illustrations built from reusable parts.** A scene made of several trees, or a diagram with several identical connector arrows, benefits from defining the reusable part once and placing many `use` instances rather than duplicating the underlying path data.
* **Any transform or event handler that should apply to a multi-shape unit as one thing.** That's squarely `g`'s job — grouping shapes that should move, style, or respond to interaction together.

Where they *don't* pull their weight: a shape you're only ever going to draw once has no reuse to gain from `defs`/`symbol`/`use` — a plain shape, styled directly, is simpler and easier to read.

## Production Considerations & Edge Cases

### The `use` Shadow Clone

Under the hood, a `use` element behaves as if the browser clones its referenced content into a shadow tree anchored at the `use` element's position — conceptually similar to how a Web Component's shadow DOM works. That model explains a couple of behaviors that otherwise look surprising:

* CSS or presentation attributes applied to the `use` element itself *can* override the original's presentation attributes — but only for properties the original element doesn't already set explicitly on itself (as seen in the [`use` Without `symbol`](#use-without-symbol) demo above, where the clone falls back to black rather than the original's inherited blue).
* An ID-based CSS selector that targets something *inside* the original element's structure — a nested `path` by its own `id`, say — does not reach into the `use` clone. The clone is a copy of the rendered result, not a live, selector-addressable mirror of the original's internal DOM.

<Warning title="Don't rely on selectors reaching through a use clone">
  If you need per-instance control over an element *inside* a referenced group, expose that control through an attribute on the `use` element (like the `fill` override above) or a CSS custom property inherited into the clone — not a selector chasing an `id` that lives inside the original's markup.
</Warning>

### Cross-Origin `use`

Everything above assumes `use` is referencing something in the *same* SVG document. `use` can also point at an external file — `href="icons.svg#icon-star"` — but that comes with a stricter requirement: the browser applies same-origin rules to cross-document `use` references, more strictly than it does to same-document ones. Referencing a `symbol` in a file served from a different origin without the right CORS headers in place will silently fail to render, rather than falling back to some partial result.

<Info title="Practical takeaway">
  For an icon sprite loaded from its own file, serve it from the same origin as the page (or with appropriate CORS headers) if you plan to reference it with `use href="icons.svg#icon-name"`. Referencing symbols defined inline in the current document never runs into this at all — same-document `href="#icon-name"` references have no origin to cross.
</Info>

## Wrapping Up

`g`, `defs`, `symbol`, and `use` turn SVG from "a flat list of shapes" into an actual graphics system with reuse and organization built in:

* **`g`:** Groups elements so a shared `transform`, presentation attribute, or event listener applies to the whole group at once — and nested groups let you isolate a transform to exactly the part of an illustration it should touch.
* **`defs`:** Holds elements meant to be referenced, not rendered directly where they're defined — the natural home for gradients, filters, clip paths, and reusable shapes.
* **`symbol` and `use`:** SVG's native component system. A `symbol`'s own `viewBox` lets every `use` instance scale independently, and each instance can carry its own position, size, transform, and color without touching the shared definition or any other instance.
* **`use` without `symbol`:** Any element with an `id` is a valid `use` target — useful for simple duplication when you don't need `symbol`'s independent `viewBox` scaling.
* **Nested `svg`:** A viewport within a viewport, useful for embedding a self-contained mini-diagram at a specific position without recalculating its internal coordinates.
* **`switch`:** A narrow, legacy-leaning tool for picking the first child whose feature or language test passes — most commonly `systemLanguage`-based localization.
* **Icon sprite systems:** A `defs` block of `symbol` icons, referenced by `use` throughout a page, is the SVG-native alternative to an icon font or repeated inline markup.
* **Production edge cases:** `use` behaves like a shadow-DOM clone — attributes on the `use` element can override the original's *unset* properties, but ID-based selectors don't reach into the clone, and cross-origin `use href` references need same-origin or CORS handling that same-document references never require.

With shapes, paths, text, and now reuse and organization covered, you have the full toolkit for building real, maintainable SVG documents — not just one-off graphics, but systems of them.
