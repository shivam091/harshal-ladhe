## Introduction

If you've already got multi-stage builds and cache-friendly instruction ordering under your belt, you've solved the two most common sources of Dockerfile bloat: shipping build-time toolchains in your runtime image, and re-running expensive steps because a `COPY` further up the file invalidated the cache. That's a solid baseline, but it's also where most Dockerfile tutorials stop.

The next tier of optimization isn't expressible in plain Dockerfile syntax — it's BuildKit-specific: persistent cache directories that survive across builds without polluting the final image, secrets that never touch a layer or the build cache metadata, runtime bases stripped to nothing but the application and its direct dependencies, and, for the layers that do ship, techniques to reduce how many there are and how much dead weight they carry.

This is **Part 5** of a six-part Docker series. It builds directly on [Writing Efficient Multi-Stage Dockerfiles](/post/docker/multi-stage-dockerfiles) and [Understanding Docker Layers and Caching](/post/docker/docker-layers-and-caching) — if multi-stage builds or the build cache still feel shaky, start there.

By the end of this post, you'll be able to:

- Use `RUN --mount=type=cache` to give package managers a persistent cache across builds without baking that cache into a layer
- Correctly combine cache mounts with the cleanup steps (like removing apt lists) that cache mounts don't replace
- Pass credentials into a build with `--mount=type=secret` instead of `ARG`/`ENV`, and explain why that matters
- Choose between a distroless base and a traditional slim base for a given service, with eyes open about the debugging tradeoff
- Explain what `docker build --squash` actually does, and why multi-stage builds are the more durable way to get the same benefit
- Write a `# syntax=docker/dockerfile:1` directive correctly and know why it's required for these features

## BuildKit: The Modern Build Engine

BuildKit has been Docker's default build backend since Docker Engine 23.0 (mid-2023) — before that, it existed as an opt-in engine enabled via `DOCKER_BUILDKIT=1`, going back several years earlier as an incrementally-adopted replacement for the legacy builder. On a reasonably current Docker install, `docker build` already routes to BuildKit transparently.

What's easy to miss is that BuildKit's *engine* and the Dockerfile *frontend syntax* are versioned separately: the engine can support a feature, but the parser won't recognize the syntax for it unless you explicitly request a newer frontend. That's what the line

<CodeBlock language="docker">
{`
  # syntax=docker/dockerfile:1
`}
</CodeBlock>

does — it must be the first line, before even a comment, and it tells BuildKit to pull the Dockerfile frontend defined by that image reference rather than falling back to whatever frontend ships with your local Docker install. Every technique in this post depends on this directive being present; miss it and `RUN --mount=...` fails to parse, because the bundled frontend simply doesn't know that flag exists.

## Cache Mounts: Persistent Package-Manager Caches Without Layer Bloat

Here's the problem cache mounts solve. Package managers like `npm`, `pip`, and `apt` maintain a local download/build cache to avoid re-fetching or re-compiling things already handled. In a normal build, that cache lives inside the writable layer the `RUN` instruction produces — so it either ships in your final image, bloating it with stuff you'll never use at runtime, or you scrub it with a trailing `rm -rf` to keep the layer small. The scrub approach works, but it throws the cache away every build, so you pay the full download/compile cost on every cache-miss even when the packages themselves haven't changed.

`RUN --mount=type=cache,target=<path>` gives you both. It mounts a directory BuildKit manages *outside* the union filesystem that becomes your image layers — present only for that `RUN` instruction, with whatever gets written there **not** committed to the resulting layer. Unlike a plain `tmpfs`, though, its contents persist across build invocations, keyed to the mount's target path. Net effect: a warm package-manager cache every build, but a layer containing only what you explicitly install elsewhere.

<CodeBlock language="docker">
{`
  # syntax=docker/dockerfile:1
  FROM node:20-slim AS build
  WORKDIR /app
  COPY package.json package-lock.json ./
  RUN --mount=type=cache,target=/root/.npm \\
      npm ci
  COPY . .
  RUN npm run build
`}
</CodeBlock>

The `npm ci` layer still gets invalidated whenever `package-lock.json` changes — cache mounts don't change layer-cache invalidation semantics. What changes is what happens *after* invalidation: instead of re-downloading every package, `npm` finds them already sitting in `/root/.npm` from the last build and mostly just re-links them, which is dramatically faster on a large dependency tree.

The same pattern applies to `apt`, with one important nuance — a cache mount only covers the actual package cache directory, not all of apt's on-disk state:

<CodeBlock language="docker">
{`
  # syntax=docker/dockerfile:1
  FROM debian:bookworm-slim
  RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \\
      --mount=type=cache,target=/var/lib/apt,sharing=locked \\
      apt-get update && apt-get install -y --no-install-recommends \\
        curl ca-certificates \\
      && rm -rf /var/lib/apt/lists/*
`}
</CodeBlock>

`/var/cache/apt` holds the downloaded `.deb` archives — the expensive-to-refetch part, and exactly what the cache mount is for. `/var/lib/apt/lists` is the package index metadata that `apt-get update` fetches; you generally want a fresh index each build rather than a long-lived cache of it, and you don't want it sitting in your shipped image either, so the `rm -rf` still earns its keep. Cache mounts eliminate redundant *downloads*; they don't eliminate the discipline of cleaning up metadata that has no reason to be in the final layer.

<Info title="Cache mount scoping and sharing">
Cache mounts are keyed by their `target` path (optionally combined with an explicit `id`), and by default that cache is shared across *all* builds on the same builder instance — different Dockerfiles and images included, as long as they mount the same target/id. If concurrent `RUN` steps could write to the same mount at once, add `sharing=locked` (serializes access) or `sharing=private` (gives each build its own copy). Because the cache lives with the builder, not the image, a fresh CI runner or a different `docker buildx` builder instance starts with a cold cache again.
</Info>

## Secret Mounts: Keeping Credentials Out of Layers

If you've ever needed a private registry token or an API key available *during* a build step — cloning a private repo, hitting an authenticated package index — the naive options are all bad: an `ARG` or `ENV` value gets recorded in the image's build history and can be recoverable from the image itself, and deleting the file in a later `RUN` doesn't remove it from earlier layers.

`--mount=type=secret` sidesteps this entirely. You declare where the secret should be readable from during a specific `RUN`:

<CodeBlock language="docker">
{`
  # syntax=docker/dockerfile:1
  RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \\
      npm ci
`}
</CodeBlock>

and supply its value at build time, outside the Dockerfile:

<CodeBlock language="bash">
{`
  docker build --secret id=npmrc,src=./.npmrc .
`}
</CodeBlock>

The secret is mounted into the container's filesystem only for the lifetime of that `RUN` instruction, is never written to any resulting image layer, and isn't recorded in the build cache metadata that would otherwise let a later `docker history` or cache export expose it. This is a narrow tool — it solves "get a credential into one build step safely," not the broader question of managing, rotating, or injecting secrets across an entire deployment pipeline, which gets its own dedicated treatment elsewhere.

## Distroless and Minimal Runtime Images

A `-slim` or `-alpine` base still gives you a functioning micro-Linux userland: a shell, a package manager, coreutils. That's convenient, but every one of those components is also attack surface and image bytes your application doesn't need at runtime. **Distroless** images — the term comes from Google's `gcr.io/distroless/*` family, though the concept generalizes — push minimalism further: the runtime base ships your language's runtime (a JRE, a Python interpreter, or nothing at all for a statically-linked Go/Rust binary) plus the direct OS-level shared libraries it needs, and nothing else. No shell, no package manager, no `ls`, no `cat`.

<CodeBlock language="docker">
{`
  # syntax=docker/dockerfile:1
  FROM node:20-slim AS build
  WORKDIR /app
  COPY package.json package-lock.json ./
  RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev
  COPY . .

  FROM gcr.io/distroless/nodejs20-debian12
  WORKDIR /app
  COPY --from=build /app /app
  CMD ["server.js"]
`}
</CodeBlock>

The payoff is a smaller image and a meaningfully reduced set of binaries an attacker could pivot to after achieving code execution inside the container — no `sh` to spawn, no `curl` to exfiltrate with, no package manager to pull in more tools. The cost is operational: `docker exec -it <container> sh` fails outright, because there's no shell binary to exec.

<Warning title="Distroless breaks your usual debugging workflow">
Because there's no shell or coreutils in the image, you can't shell in to poke around a running distroless container the way you would with a slim or Alpine base. The current workaround patterns: Docker's `docker debug` command, which attaches a separate toolbox of debugging utilities to a running container without modifying its image, or, in orchestrated environments, an ephemeral debug container (e.g. Kubernetes' `kubectl debug`) sharing the target's process namespace. Settle on your debugging story before adopting distroless in production, not during an incident.
</Warning>

## Layer Squashing

Every `RUN`, `COPY`, and `ADD` instruction produces a new layer, and layers are additive: if an earlier layer writes a large file and a later layer deletes it, the file is gone from the final filesystem view but its bytes are still physically present in the earlier layer and still counted in the image's pulled size. Layer squashing flattens a set of layers into one, so the final image reflects only the net filesystem state — no resurrectable deleted files, and often a smaller layer count and total size.

Docker has offered an experimental route to this directly: `docker build --squash`, which merges all new layers produced by a build into a single layer on top of the base image. Accessing it has historically required enabling Docker's experimental CLI/daemon features, and support has been inconsistent across Docker versions and build backends — at various points unavailable in the BuildKit builder or gated differently than in the legacy builder. Treat `--squash` as something to check current support for on your exact Docker version, not as a stable, universally-available flag.

The more durable, now more commonly recommended approach doesn't squash anything explicitly — it uses multi-stage builds to sidestep the problem. If build stages accumulate temporary files, compilers, and intermediate artifacts, none of that matters as long as those stages aren't the *final* one: only the last `FROM` (or whichever stage you target) determines what ships. A final stage built with a handful of deliberate `COPY --from=<stage>` instructions, pulling in just the finished artifacts, gets the same "no stale deleted files lying around" property that squashing chases — without experimental flags, the caching downsides of one monolithic layer, or version-dependent behavior. Most teams reach a lean image today through stage design rather than `--squash`.

## Frequently Asked Questions

### Do cache mounts get included when I push or pull an image?

No. Cache mounts exist only during the build, on the builder host; nothing written to them is committed to an image layer, so they have no effect on push/pull size or content.

---

### Can I use `--mount=type=cache` and `--mount=type=secret` together in one `RUN`?

Yes, a single `RUN` instruction can declare multiple `--mount` flags of different types; they're independent and don't interfere with each other.

---

### Is `# syntax=docker/dockerfile:1` required even if I'm not using cache or secret mounts?

Not strictly for a plain Dockerfile using only long-standing instructions, but it's cheap insurance: it gets you frontend improvements and bug fixes without depending on whatever version happens to be bundled with the local Docker install doing the build.

---

### If I use a distroless final stage, can I still run `npm install` or `apt-get` in it?

No — those tools don't exist in the image. Any package installation has to happen in an earlier build stage that does have a shell and package manager; only the resulting artifacts get copied into the distroless final stage.

---

### Does squashing layers improve build cache reuse?

No, generally the opposite — squashing collapses layers after the fact, which can reduce how much of a squashed image's history BuildKit can reuse as cache for a future build compared to keeping instructions in discrete, individually cacheable layers.

## Conclusion

Cache mounts, secret mounts, distroless bases, and layer squashing all attack the same tension in Dockerfile design: builds want to reuse work, images want to ship as little as possible, and those goals conflict unless your tooling separates "what helps the build" from "what ends up in the shipped layer." BuildKit's mount types are that separation mechanism, and the modern preference for multi-stage builds over `--squash` applies the same idea to layer hygiene — design stages so nothing unwanted is ever adjacent to the final artifacts, rather than cleaning it up after the fact.

**Key Takeaways:**

- BuildKit is the default engine on Docker Engine 23.0+, but advanced mount syntax still requires an explicit `# syntax=docker/dockerfile:1` directive as the Dockerfile's first line
- `RUN --mount=type=cache,target=<path>` persists a package-manager cache across builds without that cache landing in any image layer
- Cache mounts are keyed by target path (or an explicit `id`) and shared across builds on the same builder by default; use `sharing=locked` or `sharing=private` for concurrent access
- Cache mounts don't remove the need for other cleanup — apt's package cache benefits from a cache mount, but its index metadata under `/var/lib/apt/lists` still needs an explicit `rm -rf`
- `RUN --mount=type=secret` paired with `docker build --secret` keeps credentials out of image layers and build cache metadata, unlike `ARG`/`ENV`
- Distroless images shrink attack surface and size by dropping the shell and package manager, but break `docker exec ... sh`-style debugging — plan around `docker debug` or an ephemeral debug sidecar
- `docker build --squash` is experimental, requires enabling experimental features, and has had inconsistent support across Docker versions — don't treat it as a stable default
- Multi-stage builds achieve squashing's practical benefit — no stale files from earlier steps — as a natural side effect of only shipping the final stage, which is why they're the more commonly recommended approach today
