## Introduction

By default, Docker only knows whether a container's main process is *running* — not whether it's actually ready to do useful work. A Node process can be up and listening on its port while still failing every request because a database connection hasn't finished initializing. The `HEALTHCHECK` instruction closes that gap: it runs a command on a schedule, and Docker reports the container as `healthy`, `unhealthy`, or `starting` based on its exit code.

<RainbowDivider />

## The Instruction

<CodeBlock language="docker">
{`
  HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \\
    CMD node -e "require('http').get('http://localhost:3000/health', (res) => process.exit(res.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"
`}
</CodeBlock>

* **`--interval`** — how often to run the check once the container is up (default: `30s`).
* **`--timeout`** — how long a single check attempt is allowed to run before it's treated as a failure (default: `30s`).
* **`--start-period`** — a grace window right after container start during which failures don't count toward `--retries`, for slow-starting apps (default: `0s`).
* **`--retries`** — consecutive failures required before the container flips from `healthy` to `unhealthy` (default: `3`).

The check itself runs a small inline Node script rather than `curl`, since many slim/Alpine base images don't ship `curl` by default and installing it just for a health check is unnecessary overhead — a zero-dependency script using the runtime that's already there is usually the leaner choice.

<RainbowDivider />

## A Database Variant

For images that already ship their own readiness CLI, use that directly instead of reaching for HTTP. Postgres is the common example:

<CodeBlock language="docker">
{`
  HEALTHCHECK --interval=5s --timeout=5s --retries=5 \\
    CMD pg_isready -U postgres || exit 1
`}
</CodeBlock>

<RainbowDivider />

## Seeing It in Action

Once built, `docker ps` shows the check's current status alongside the container:

<CodeBlock language="bash">
{`
  $ docker ps
  CONTAINER ID   IMAGE     STATUS
  a1b2c3d4e5f6   myapp     Up 2 minutes (healthy)
  b2c3d4e5f6a7   postgres  Up 2 minutes (starting)
`}
</CodeBlock>

`(starting)` means the container is still inside its `--start-period` grace window; `(healthy)`/`(unhealthy)` reflect the most recent check result once that window has passed.

<RainbowDivider />

## Using It with Docker Compose

Plain `depends_on` only waits for a container to *start*, not for whatever it depends on to be *ready*. Pairing a `healthcheck:` with `condition: service_healthy` fixes that:

<CodeBlock language="yaml">
{`
  services:
    web:
      build: .
      depends_on:
        db:
          condition: service_healthy

    db:
      image: postgres:16-alpine
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U postgres"]
        interval: 5s
        timeout: 5s
        retries: 5
`}
</CodeBlock>

Compose won't start `web` until `db`'s health check reports healthy — a far more reliable substitute for a manual `sleep` or a retry loop bolted onto application startup code.

<RainbowDivider />

## Production Considerations & Edge Cases

* **A health endpoint should be cheap.** Don't have `/health` re-verify every downstream dependency on every check — a check that's too expensive or too strict can flap a perfectly fine container into `unhealthy` under load.
* **`--start-period` matters more than it looks.** Without it, a service with a genuinely slow cold start (JIT warmup, cache priming, migrations) can accumulate enough failures to be marked unhealthy before it's ever had a fair chance to come up.
* **An `unhealthy` container isn't automatically restarted by plain Docker.** That behavior comes from an orchestrator (Compose with a restart policy, Kubernetes liveness probes, Swarm) acting on the health status — `HEALTHCHECK` alone only reports state, it doesn't enforce a response to it.

<RainbowDivider />

## Key Takeaway

`HEALTHCHECK` turns "is the process running" into "is the process actually ready," which is what `depends_on`'s `condition: service_healthy` and most orchestrators actually need to sequence startup correctly. Keep the check itself cheap and give slow-starting services a real `--start-period`.
